# read — App Brief

## What it is

A minimalist web app for reading books as PDFs and journaling against them. You read in the left pane, select a passage, and write about it in the right pane. Entries stay anchored to the passage that prompted them, so years later you can look back at a book and see everything it made you think.

Single user, personal project. Runs entirely in the browser. Google Drive holds the files. No backend server.

## Principles

1. **Reading is the primary act.** The journal is the second thing on screen, never the first.
2. **Keyboard-driven.** Select, one key, write, save. No floating toolbars over selections.
3. **Quiet by default.** Typography-led, generous margins, restrained colour. This is a room to think in, not a dashboard product.
4. **The writing outlives the app.** Entries sync to Drive as readable files.

## Routes

### 1. Dashboard (`/`)

The landing page. Answers "am I keeping this up?"

- **Streak** — consecutive days with at least one entry. Large, quiet, top of page.
- **Words journaled** — bar or area chart, daily totals, last 90 days.
- **Currently reading** — 1–3 book cards with cover, title, and progress. Clicking resumes at the last page.
- **Recent entries** — last 5, showing heading, book, and date.

Empty state matters here. A new user has no streak and no graph. Show a single invitation to add their first book rather than a grid of zeroes.

### 2. Library (`/library`)

Books grouped by genre. Genres are freeform strings, not a fixed enum. Expect: faith, leadership, detective, biography, philosophy.

- Genre sections with a heading and a row/grid of book cards.
- Book cards show a cover, title, author, and a thin progress bar.
- **Primary action:** a drop zone or button to upload a PDF. Should also accept a file dragged anywhere onto the page.
- **Secondary action:** a smaller "Add from Drive" link that opens the Google Picker.
- After upload, a small dialog asks for title, author, and genre. Pre-fill the title from the filename and the PDF metadata where available.

Covers are generated by rendering page 1 with pdf.js to a canvas and storing a downscaled data URL. No cover art needs sourcing.

### 3. Reader (`/book/:bookId`)

The main screen. A resizable horizontal split, position persisted.

**Left pane — the book.** Continuous scroll of reflowed text (or PDF canvas in page mode). Running header, page indicator, jump-to-page. Passages that already have entries get a subtle highlight.

**Reading controls.** Text size adjustment is required, not optional; the mockup's 15.5px is fine for scanning and small for an hour of reading. Offer three or four steps up to about 20px and persist the choice. Add a sepia and a dark theme alongside the default; the palette below only covers light.

Set body text left-aligned rather than justified. Justification in a 640px column with browser hyphenation produces uneven word spacing and rivers, which is exactly the kind of thing that makes long reading tiring without the reader knowing why.

**Right pane — the journal.** Two modes:
- *Book view* (default): all entries for this book, newest first, each showing heading, excerpt, and body.
- *Composer*: opens when a new entry starts.

**The core interaction:**
1. Select text in the PDF.
2. Press `E` (or `Ctrl+Enter`).
3. The composer opens in the right pane with the excerpt and anchor already attached, cursor in the heading field.
4. `Ctrl+Enter` saves. `Esc` discards.

Also support starting a free-standing entry with no selection.

**Voice input.** A push-to-talk control in the composer. Hold to speak, release to stop; transcript streams into the body field as you talk. Build this last — it's the smallest piece.

## Data model

```ts
type Book = {
  id: string;
  driveFileId: string;
  viewMode: "reflow" | "page";   // decided at import, user-overridable
  title: string;
  author?: string;
  genre: string;
  coverDataUrl?: string;
  pageCount?: number;
  lastLocation: number;          // character offset, not page number
  addedAt: string;      // ISO UTC
  lastOpenedAt?: string;
};

type Anchor =
  | { kind: "quote"; bookId: string; offset: number;
      exact: string; prefix: string; suffix: string }
  | { kind: "location"; bookId: string; offset: number }
  | { kind: "free" };

type Entry = {
  id: string;
  bookId?: string;      // undefined for free-standing entries
  title?: string;       // user-written heading, e.g. "Romans 8 — on suffering"
  ref?: string;         // normalized reference parsed from title, e.g. "Rom.8"
  body: string;         // markdown
  anchor: Anchor;
  excerpt?: string;     // snapshot of the selected text at write time
  displayLocation?: string;  // frozen label, e.g. "Psalms 22 · p. 612"
  wordCount: number;    // computed on save, never at read time
  source: "typed" | "spoken" | "mixed";
  tags: string[];
  createdAt: string;    // ISO UTC
  updatedAt: string;
};
```

**Why offsets instead of page numbers:** `offset` is a character index into the book's normalized extracted text. It survives reflow, font size changes, and window resizing, none of which page coordinates do. Page numbers are computed for display only.

**Why `displayLocation` is frozen:** the human-readable label shown on an entry ("Psalms 22 · p. 612") is written once at save time and never recomputed. If re-extraction ever shifts by a page, old entries keep saying what they said.

**Why the anchor is a union:** it keeps free-standing entries from being a special case, and leaves room to add a `verse` variant later without disturbing existing data.

**Why `ref` exists:** headings drift ("Romans 8", "Rom 8", "romans 8 again"). Parse the heading on save against the 66 book names plus common abbreviations and store a normalized form. If nothing matches, leave it undefined — that's correct for a leadership book.

## Text rendering — read this before building the reader

The mockup does **not** display PDF pages. It extracts the text and re-sets it in the app's own typography, inside a card styled to look like a page. This is the right target, but it is also the single hardest part of the app, and it fails in specific predictable ways.

**Two view modes per book. Both must exist.**

- **Reflow** (default): extracted text, re-typeset in Lora, paragraph structure reconstructed. What the mockup shows.
- **Page** (fallback): the actual PDF rendered to canvas via pdf.js.

**Decide the mode at import, automatically.** After upload, extract text from a sample of pages and check: average characters per page, proportion of pages with any text, and whether x-positions cluster into more than one column. Scanned books have no text layer at all and must go to page mode. Multi-column academic PDFs extract in the wrong reading order and should too. Tell the user which mode a book landed in and let them override.

**Paragraph reconstruction** from pdf.js `getTextContent()`, which returns positioned text items with no paragraph or heading structure:

1. Group items into lines by y-coordinate.
2. Compute median line gap, median left edge, median glyph height for the book.
3. Start a new paragraph when the vertical gap exceeds ~1.4× the median, or the line is indented past the median left edge, or the previous line ended well short of the right margin.
4. De-hyphenate: a line ending in `-` followed by a line starting lowercase joins without the hyphen.
5. Strip running headers and footers: lines in the top or bottom ~8% of the page whose text repeats across many pages or is a bare number.
6. Treat lines with glyph height >1.2× the body median as headings.
7. Normalize ligatures (ﬁ, ﬂ) and smart quotes.

**Page numbers become display-only.** Once text reflows, "page 612" is a label derived from the source, not a position. Anchors must not depend on it.

**No backend.** Google Identity Services issues a browser-side access token; the Drive REST API supports CORS and is called directly.

**Scope: `https://www.googleapis.com/auth/drive.file` only.** Non-sensitive, no verification required. Do *not* request `drive` or `drive.readonly` — both are restricted scopes requiring OAuth verification plus an annual paid CASA security assessment.

`drive.file` grants access to files the app creates, plus files the user picks via the Google Picker. That's sufficient for both the upload path and the add-from-Drive path.

**Layout in Drive:**
```
read/
  library.json          # book catalog
  books/                # uploaded PDFs
  journal/
    2026-09.md          # one file per month
```

**Sync model:** IndexedDB is the working copy the UI reads from. Drive is the durable store. Write through to Drive on save, debounced. One file per month so saving doesn't rewrite the whole journal.

**PDF loading:** fetch bytes via `files/{id}?alt=media`, wrap in a Blob, hand to pdf.js. Cache the blob in Cache Storage so a book isn't re-downloaded every session.

**Upload:** resumable upload (`uploadType=resumable`). Multipart caps out around 5MB and book PDFs exceed that routinely. Show a progress bar.

## Gotchas to handle

- **Token expiry.** Browser-side tokens last ~1 hour with no refresh token. Catch 401s, silently request a new token, retry. If the PDF blob is cached, reading continues uninterrupted and only saving is affected.
- **Streak timezone.** Store `createdAt` in UTC, bucket by *local* date. Use a 4am day boundary rather than midnight, so a 12:30am entry counts for the day it feels like.
- **Word count.** Denormalized on the entry at save time. Never parse entry bodies during dashboard render.
- **PDF anchoring.** pdf.js gives a text layer of positioned spans with no semantic structure. Take `selection.toString()` as `exact`, plus ~30 characters either side from the page's text content as `prefix`/`suffix`. Re-find later by searching page text for that triple.
- **Voice transcripts.** Store raw. Do not auto-punctuate or clean up — a silent rewrite will eventually change something that was meant.
- **Speech privacy.** Request on-device processing via `SpeechRecognition.install({ langs: ["en-US"], processLocally: true })` so audio isn't sent to a web service.

## Stack

- Vite + React + TypeScript
- Tailwind
- `react-pdf` (pdf.js) for rendering and text extraction
- `react-resizable-panels` for the split
- Dexie for IndexedDB
- Recharts for the dashboard graph
- Google Identity Services + Drive REST API v3
- Deployed on Vercel (static build; add the Vercel domain to the OAuth client's authorized origins)

### Design tokens (from the approved mockup)

Headings **Cormorant Garamond** 600, body **Lora** 400, both from Google Fonts under the SIL Open Font License. Self-host them via `@fontsource` rather than the Google CDN so reading doesn't depend on a third-party request.

```
--color-bg:      #f3f2f2
--color-surface: #eae9e9
--color-text:    #201f1d
--color-accent:  #b68235
```

Warm off-white rather than pure white, near-black rather than black. Keep it that way; it's what makes long sessions comfortable.

## Not in v1

No sharing, no multi-user, no comments, no accounts beyond the single Google sign-in. No mobile layout — this is a desktop-width app. No highlights sidebar separate from entries. No AI features. No full-text search across books; search across *entries* only, and even that can wait.
